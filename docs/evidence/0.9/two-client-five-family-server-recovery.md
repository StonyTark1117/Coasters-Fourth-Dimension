# FD902 two-client five-family server recovery

This checkpoint connects two independent packaged clients, **Dev** and
**Observer**, to a fresh dedicated server for each original family: Arrow,
Legacy ZacSpin, Free Spin, Revised ZacSpin, and the four-chassis PAX shuttle.
The server admits both identities, assigns them to distinct native seats on one
carrier, dispatches the occupied vehicle, removes its exact matching Coasters
connection while it moves, rebuilds the exact curve, runs the production repair
action, and performs physical realignment.

## Result

Every family passed the server-authoritative sequence. At support loss the
server recorded both identities as retained under closed restraints; after
repair and realignment it recorded `ridersRetained=2`. PAX additionally moved
and tracked all four linked chassis before the lead lost support. The concise
per-family server markers are in
[two-client-five-family-server-recovery.txt](two-client-five-family-server-recovery.txt).

This is strong evidence for concurrent native-seat retention and production
recovery operations with two real connected clients. It deliberately does not
claim ordered post-repair observation on both clients: the client validation
guard must first require loss → repair → realignment in that order. The next
checkpoint will replay this same matrix against that guard.
