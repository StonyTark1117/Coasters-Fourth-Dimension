# Roadmap execution guides

These guides decompose the roadmap's open packages into ordered, complete outcomes.
They do not change scope, acceptance criteria, dependency order or publication
permission. All adopted vehicle/cart and seat-motion styles remain before 1.0;
moving-track mechanisms remain after 1.0. Completed packages were not rewritten.

## Find the work

1. Read the [current assignment/remaining-case queue](../CURRENT-QUALIFICATION.md#current-work-queue),
   confirm the owner and inspect the package's current status in [ROADMAP.md](../../ROADMAP.md).
   Historical “still open” notes are not assignments. Do not bulk-add future cards
   to the active queue or treat an unrecorded owner as proof of availability.
2. Open the package's **Execution steps** or **Steps** link in the roadmap, or find
   its FD ID in the guide table below. Read only the card's relevant inputs first;
   follow evidence links for the claims being worked rather than rereading all history.
3. Follow actual prerequisites, including integrated shared-contract proof. A stage
   number or an unrelated incomplete gate does not block otherwise ready work.
4. Own the complete assigned outcome and continue through compatible steps. Cite
   a step as “FD1802A, step 3” in the existing next-action entry when useful. Steps
   are procedural references, not new FD IDs, work assignments, approvals or runs.
   Stay within the assigned package and its required children; an aggregate gate's
   other inputs do not become part of a child assignment. For 0.4, use the
   [FD402/FD403 boundary](0.4-core.md#choose-the-assigned-package).
5. Reuse accepted work, close covered criteria and hand off the integrated result.
   Stop when the existing package criterion is satisfied. Leave only the precise
   blocker/remaining claim in the queue when continuation really is blocked.

Each open roadmap heading/table package has one execution card. Existing smaller
case IDs (for example FD402B1–B7) remain in their current queue and acceptance
matrix; their parent card directs execution without cloning their assignments.
Cross-stage packages have one home: all family discovery/specifications and
FD904C1 are in 0.5; FD501B–D and FD1701A in 0.8; FD501E–H in 0.9;
FD917 in pre-1.0 production; FD904C2 in final qualification; FD1701B/C and their parent in 1.2.

When source requirements evolve, update the affected card with the canonical
package. A card is an explanation of its existing criterion, not authority to add
scope. Once a package closes, its card remains a reusable procedure; its continued
presence never reopens work. Read status from the roadmap, not from this guide's
original inventory. Design-card questions are resolved in their specification
packages; the guide does not invent mechanical dimensions or certify prototypes.

## Execution and stopping rules

- Shared runtime, persistence, eligibility and seat/camera changes have one owner
  at a time. Dependent implementation consumes the integrated `main` handoff,
  not another agent's unfinished checkout. Stable specifications/dimensions can
  unblock independent content before final mechanics/art reconciliation.
- Start with retained worlds, prototypes, code and accepted evidence. Source links
  identify current entry points, not mandated names for future classes or a new
  framework project. Keep stable persisted identities; implement any necessary
  migration only in its bounded owning package.
- Native checks establish mechanics/invariants; connected clients establish actual
  player input, rendering and rider synchronization. A shared-contract occupied
  handoff is the feature's existing required evidence, moved early and reused by
  later acceptance. Functional geometry/controls are needed; decorative polish
  can follow. Two-client claims require two real clients under current host rules.
- Choose the smallest check for a named unresolved or affected claim. A numbered
  step does not automatically mean a build, launch or test. Compatible observations
  can close several claims; separate construction, mechanics, rendering and
  persistence records can establish a complete outcome. Do not keep a fully
  covered task open because one record calls itself a bounded “slice.”
- New JAR hashes, milestones, docs, fixture-only edits and unrelated changes do not
  reset acceptance. Reopen only the specific claim invalidated by a named change
  or defect; a passing targeted fix closes it without resetting siblings/parents.
  Two inconclusive attempts with the same approach require diagnosis before another
  launch. No card creates a default repetition count or a Cartesian profile matrix.
- Parent/outcome gates reconcile their declared inputs. Run only an outstanding
  criterion or genuinely unproven interaction; do not replay child workflows.
  Full release qualification remains late, and equivalent accepted checks count.
  Named required failures block their consumer; optional polish stays separate.
- Store outputs in the owning package/design/current evidence records; no extra
  manifest, card checklist or reviewer approval is required for routine closure.
  At handoff, name the integrated revision/contracts, accepted evidence and actual
  remaining gap. Update the existing queue, then stop when the criterion passes.

## Keeping the guides consistent

For a roadmap change, check package-to-card coverage, links, actual prerequisites
and release allocation. Keep closed statuses and historical evidence intact.
Documentation-only changes need documentation checks, not Minecraft builds/runs.
New scope receives a canonical package first, then one card in its delivery guide.
For FD2001's future shipping allocations, add each permanent FD2007 suffix gate
with its finite list and its own card; do not invent those increments in advance.
