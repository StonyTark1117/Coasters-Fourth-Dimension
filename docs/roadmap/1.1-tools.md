# 1.1 — Builder and operator tools

[Guide index and execution rules](README.md) · [Canonical roadmap](../../ROADMAP.md) · [Active assignments](../CURRENT-QUALIFICATION.md#current-work-queue)

Saved settings, original appearance choices and a unified panel extend existing interfaces. These tools do not postpone any adopted 1.0 vehicle or reopen accepted editing, art or telemetry.

Card order helps navigation; actual prerequisites determine readiness. These are
procedures, not a second status tracker. Apply the index's evidence and stopping
rules to every step; already-covered steps do not require another run.

## FD1602

**Outcome:** Named shareable motion/tuning presets that apply through existing setting contracts.

**Start conditions:** FD105, FD203; integrated consumer setting contracts

**Read first:** [canonical scope, status and completion criteria](../../ROADMAP.md#fd1602); [ProfileEditor](../../src/main/java/dev/fourthdimension/track/ProfileEditor.java), [AppearanceEditor](../../src/main/java/dev/fourthdimension/integration/AppearanceEditor.java), [RideTelemetry](../../src/main/java/dev/fourthdimension/integration/RideTelemetry.java), [RideOperations](../../src/main/java/dev/fourthdimension/integration/RideOperations.java), [tool scope](../../PLAN.md#d19-vehicle-variants-tools-and-scenery-facing-yaw).

**Ordered steps:**

1. Enumerate the bounded settings supported by each declared family/variant and consume their integrated editors; keep world/blueprint copying outside scope.
2. Implement save/name/export/import with format version, family/variant and numeric-bound checks.
3. Require explicit rebinding of world-specific references; apply permissions and current edit-state/revision checks before mutation.
4. Expose normal player save/import/apply controls and guidance; incompatible imports must leave current state intact.
5. Verify representative round-trips, rebinding and rejection paths, then record the declared settings/profile list.

**Validation:** Focused serialization/bounds/atomic-rejection checks and normal client application. Unchanged underlying motion acceptance carries forward.

**Finish and handoff:** Close presets for [FD1605](1.1-tools.md#fd1605); no new ride-physics or construction campaign. Record evidence and closure in the canonical package/current queue as applicable, then stop.

## FD1603

**Outcome:** Finite original palette/livery choices with preview, persistence and fallback.

**Start conditions:** Stable consumer material/appearance interfaces; [FD910](0.9-presentation.md#fd910) only for its optional adapter

**Read first:** [canonical scope, status and completion criteria](../../ROADMAP.md#fd1603); [ProfileEditor](../../src/main/java/dev/fourthdimension/track/ProfileEditor.java), [AppearanceEditor](../../src/main/java/dev/fourthdimension/integration/AppearanceEditor.java), [RideTelemetry](../../src/main/java/dev/fourthdimension/integration/RideTelemetry.java), [RideOperations](../../src/main/java/dev/fourthdimension/integration/RideOperations.java), [tool scope](../../PLAN.md#d19-vehicle-variants-tools-and-scenery-facing-yaw).

**Ordered steps:**

1. Select the finite original choices and supported vehicle/material interfaces; isolate [FD910](0.9-presentation.md#fd910)-specific integration from standalone choices.
2. Implement player selection/preview and persisted appearance without changing mechanical identity or seat ownership.
3. Implement the specified missing-provider fallback for optional appearance and retain standalone original choices.
4. Apply [FD916](0.9-presentation.md#fd916)'s existing visual checklist to changed assets and affected poses, using accepted unchanged views.
5. Check normal selection/reopen/fallback and document the choices; no arbitrary texture uploads or branded replicas are added.

**Validation:** Affected resources/visuals and targeted client selection/persistence checks. New liveries do not reopen the accepted 1.0 art baseline.

**Finish and handoff:** Close colors/liveries for [FD1605](1.1-tools.md#fd1605); optional addons remain optional. Record evidence and closure in the canonical package/current queue as applicable, then stop.

## FD1604

**Outcome:** One usable operator interface reflecting authoritative whole-consist state.

**Start conditions:** FD401D, FD106; integrated control/readiness contracts

**Read first:** [canonical scope, status and completion criteria](../../ROADMAP.md#fd1604); [ProfileEditor](../../src/main/java/dev/fourthdimension/track/ProfileEditor.java), [AppearanceEditor](../../src/main/java/dev/fourthdimension/integration/AppearanceEditor.java), [RideTelemetry](../../src/main/java/dev/fourthdimension/integration/RideTelemetry.java), [RideOperations](../../src/main/java/dev/fourthdimension/integration/RideOperations.java), [tool scope](../../PLAN.md#d19-vehicle-variants-tools-and-scenery-facing-yaw).

**Ordered steps:**

1. Map existing occupancy, restraints, power, fault, recovery and readiness telemetry into the panel; retain whole-consist semantics.
2. Present actionable dispatch-denial reasons and accurately unavailable optional controls.
3. Route commands through existing server authority, permission and revision validation; do not add a bypass for panel input.
4. Implement normal player navigation/commands and guidance; reconcile representative station/shuttle/recovery controller paths.
5. Check UI state against authoritative telemetry and affected request/denial behavior; reuse accepted source formatting and unchanged operations.

**Validation:** Native request validation plus representative connected-client panel interaction; distinct controller paths matter, not every family × profile combination.

**Finish and handoff:** Close the panel for [FD1605](1.1-tools.md#fd1605) without replacing accepted telemetry/operation systems. Record evidence and closure in the canonical package/current queue as applicable, then stop.
